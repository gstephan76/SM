# OpenShift Service Mesh 3.4 observability

Canonical observability stack for:

- OpenShift Container Platform 4.22
- Red Hat OpenShift Service Mesh 3.4.x; fresh installs pin Istio 1.30.4
- Kiali Operator provided by Red Hat 2.27
- Red Hat build of OpenTelemetry Operator 0.152.x or 0.158.x
- Tempo Operator 0.21.x or 0.22.x
- OpenShift User Workload Monitoring
- OpenShift Data Foundation / NooBaa object storage
- OpenShift Service Mesh Console (OSSMC) plugin (default)
- OpenShift distributed tracing console UI (default)

The historical files directly under `v3/` and the older POC files directly under
`v3/v3.4/` are not used by this deployment. The authoritative deployment is the
numbered set under `manifests/`, `templates/`, `storage/odf/`, `optional/`, and
`scripts/`.

## Supported data paths

```text
Envoy/Istio proxy metrics
  -> /stats/prometheus
  -> PodMonitor / ServiceMonitor
  -> OpenShift User Workload Monitoring
  -> Prometheus / Thanos
  -> Kiali

Envoy/Istio traces
  -> OTLP/gRPC :4317
  -> OpenTelemetry Collector
  -> authenticated OTLP/gRPC :8090
  -> Tempo Gateway
  -> TempoStack
  -> ODF / NooBaa S3

Kiali
  -> Thanos Querier :9091 using the Kiali service-account token
  -> Tempo Gateway :8080 using the Kiali service-account token
```

Grafana is intentionally not part of the core stack. Two OpenShift console integrations are deployed by default:

- `OSSMConsole/ossmconsole`, managed by the Kiali Operator, provides the **Service Mesh** navigation and embedded Kiali views.
- `UIPlugin/distributed-tracing`, managed by the Cluster Observability Operator, provides **Observe -> Traces**.

## Security and RBAC contracts

The core deployment creates explicit roles **and role bindings**:

- `tempo-mesh-traces-writer`
  - `CREATE` on tenant resource `tempo.grafana.com/mesh`, `resourceNames: traces`
  - bound to `system:serviceaccount:istio-system:otel-collector`
- `tempo-mesh-traces-reader`
  - `GET` on tenant resource `tempo.grafana.com/mesh`, `resourceNames: traces`
  - bound to `system:serviceaccount:istio-system:kiali-service-account`
- `cluster-monitoring-view`
  - bound to `system:serviceaccount:istio-system:kiali-service-account`

The optional OpenShift distributed tracing UI can additionally bind
`system:authenticated` to `tempo-mesh-traces-reader`. That is deliberately
optional because it grants every authenticated OpenShift user tenant-level trace
read access. Replace the subject with a narrower Group/User when appropriate.

ODF credentials are generated by the ObjectBucketClaim and are never committed.

## Configure

```bash
cd v3/v3.4

cp env.example .env
uuidgen
vi .env
```

Set the generated UUID as `TEMPO_TENANT_ID` and keep it stable for the lifetime
of `TempoStack/mesh`.

The default mesh namespaces are:

```bash
MESH_NAMESPACES="istio-system bookinfo"
```

Add every namespace whose Istio sidecars must be scraped.

### Existing Istio control plane

The default is:

```bash
APPLY_MESH_BASE=0
```

In this mode the scripts refuse to continue unless the existing `Istio` and
`IstioCNI` resources are Ready, pinned to an explicitly supported Istio 1.30 patch (v1.30.3 or v1.30.4), and the live Istio resource
already defines the required `otel-tracing` provider at:

```text
otel-collector.istio-system.svc.cluster.local:4317
```

If you intentionally want this bundle to reconcile those resources:

```bash
APPLY_MESH_BASE=1
```

Fresh reconciliation uses the manifest-pinned `v1.30.4`. Existing healthy
`v1.30.3` installations remain accepted in preserve mode so the older validated
cluster is not upgraded implicitly.

## Validate before applying

Load `.env` automatically by keeping it in this directory, then run:

```bash
./scripts/check-prereqs.sh
./scripts/render.sh
./scripts/validate.sh
```

`validate.sh` performs shell syntax checks, authorization checks, selectorless
Telemetry conflict detection, and **server-side dry-run** validation against the
CRDs actually installed on the cluster. On a brand-new cluster, Kubernetes cannot
server-dry-run namespaced objects until their target Namespaces exist. For only
that bootstrap condition, `validate.sh` performs strict client dry-run validation
and marks the server checks as deferred. `apply.sh` then creates the three target
Namespaces and reruns `validate.sh`, requiring the complete server-side dry-run to
pass before it applies user-workload monitoring, Istio, Tempo, OTel, Kiali, or UI
resources.

The prerequisite gate intentionally accepts only the operator families exercised
by the two supported baselines: OpenTelemetry 0.152.x/0.158.x and Tempo
0.21.x/0.22.x. A newer operator family must be added deliberately after its CRDs
and the complete server-side/E2E validation path have been reviewed.

## Apply

```bash
./scripts/apply.sh
```

The script executes the numbered deployment contract. Operator-managed CRs are gated on their authoritative status conditions, their generated workloads/services are checked separately, and timeouts dump CR/pod/event diagnostics. The setup is idempotent and can be rerun after a partial failure.

## Final E2E acceptance gate

`RUN_E2E=1` is the default and `apply.sh` runs `scripts/e2e-check.sh` only after the complete readiness postcheck. When Bookinfo is enabled the route URL is discovered automatically.

The test must prove **this run**, not merely observe stale telemetry. It verifies:

1. the external Bookinfo `/productpage` response and page content;
2. an independent in-mesh `ratings -> productpage` service request;
3. `E2E_REQUESTS` normal ingress requests with the configured 10% sampler and no more than `E2E_MAX_HTTP_FAILURES` failures;
4. multiple forced-sampled requests carrying unique known B3 trace IDs;
5. exact Tempo retrieval of every forced trace ID;
6. service-chain membership for ingress, productpage, details, reviews, plus at least one trace including ratings;
7. an `x-b3-sampled: 0` negative control that must not be stored;
8. a separate bounded random-sampling search window requiring at least `E2E_MIN_RANDOM_TRACES` traces;
9. no OTel export/auth/TLS/drop errors since the E2E start time;
10. a **before/after** Thanos query proving `istio_requests_total{destination_service_namespace="bookinfo"}` increased by at least `E2E_MIN_METRIC_DELTA` during the test;
11. a final full readiness postcheck.

The exact-trace and before/after-metric gates prevent unrelated historical traces or counters from satisfying the test.

## OpenShift Service Mesh console

The Service Mesh menu is **not** created by the `Kiali` CR alone. The supported setup creates:

```yaml
apiVersion: kiali.io/v1alpha1
kind: OSSMConsole
metadata:
  name: ossmconsole
  namespace: openshift-operators
spec:
  version: default
  kiali:
    serviceName: kiali
    serviceNamespace: istio-system
    servicePort: 20001
```

`ENABLE_MESH_CONSOLE=1` is the default. Readiness requires `OSSMConsole/ossmconsole` to report `Successful=True`, the generated `ConsolePlugin/ossmconsole` to exist, and its backend Service to have ready endpoints. Refresh the OpenShift console after first installation.

## OpenShift tracing UI

The Cluster Observability Operator distributed tracing UI plugin is enabled by default and is distinct from OSSMC:

```bash
ENABLE_TRACING_UI=1
```

Kiali renders its `View in Tracing` links with `tempo_config.url_format: openshift` and the discovered OpenShift console Route. Set `ENABLE_TRACING_UI=0` only to opt out.

To also use the example broad reader binding:

```bash
ENABLE_TRACING_UI_RBAC=1
```

For production, prefer leaving `ENABLE_TRACING_UI_RBAC=0` and editing
`optional/15-tempo-console-reader-rbac.yaml` to target the intended user group.

## UWM safety

`manifests/01-user-workload-monitoring.yaml` is the declarative baseline for a
cluster without `cluster-monitoring-config`.

If that ConfigMap already exists, `scripts/enable-uwm.sh` **does not overwrite
it**. It requires `enableUserWorkload: true` to already be present so unrelated
cluster monitoring configuration cannot be destroyed.

## Secret handling

Never commit:

- `.env`
- ODF access keys
- rendered Secret manifests
- service-account tokens
- S3 credentials


## Operator-managed observability

`TempoStack/mesh` enables operator-created `ServiceMonitor` and `PrometheusRule` objects for Tempo components. `OpenTelemetryCollector/otel` enables operator-created Collector monitoring. The Collector is bounded to a 512 MiB pod limit with a 400 MiB memory-limiter hard limit and uses the non-deprecated `otlp_grpc` exporter identifier.

Tempo tenant permissions are verified with Kubernetes `SubjectAccessReview`. `oc auth can-i` is intentionally not used for `tempo.grafana.com/mesh` because this is a synthetic authorization resource consumed by the Tempo gateway and is not present in Kubernetes API discovery.

## Bookinfo setup

Bookinfo is part of the supported setup path by default (`DEPLOY_BOOKINFO=1`).
The repository vendors the Red Hat-documented sidecar-mode Bookinfo sample and
its gateway resources so installation does not depend on mutable remote YAML at
runtime:

- `bookinfo/00-bookinfo.yaml` — Red Hat OSSM 3.4 Bookinfo sample, upstream blob `28ac4f6828e21717e0198bda2a9ac7f4694458af`.
- `bookinfo/01-ingress-gateway.yaml` — Sail gateway-injection sample, upstream blob `009cfc72950fdede8c4c7fec2e0d54c098d66181` at vendoring time.
- `bookinfo/02-bookinfo-gateway.yaml` — Istio `Gateway` + `VirtualService`, upstream blob `54e86888c651268356911772fdca379f7aa8d23e`.
- `bookinfo/03-route.yaml` — declarative OpenShift `Route` equivalent to `oc expose service istio-ingressgateway`.

The `bookinfo` Namespace is labeled `istio-discovery=enabled` and
`istio-injection=enabled`. `apply.sh` waits for all Bookinfo deployments,
sidecars, service endpoints, the injected ingress gateway, the Istio Gateway and
VirtualService objects, and Route admission before final validation.

See [VALIDATION.md](VALIDATION.md) for the complete readiness and final E2E
acceptance contract.

## Release-tolerant apply/readiness behavior

The deployment helpers use API-qualified resource identities and release-tolerant readiness checks. In particular, Bookinfo accepts Istio as either a classic or Kubernetes native sidecar, Service backends are read from EndpointSlice with Endpoints fallback, and Istio Gateway resources are always queried through `networking.istio.io` to avoid collisions with Kubernetes Gateway API. Generic waits parse `TYPE/NAME` and call `oc get TYPE NAME`, and individual API requests are bounded by `KUBE_API_REQUEST_TIMEOUT` (default `15s`).
