# OpenShift Service Mesh 3.5 observability

Canonical observability stack for:

- OpenShift Container Platform 4.22
- Red Hat OpenShift Service Mesh 3.5.x; new mesh reconciliation targets `v1.31-latest`
- Kiali Operator provided by Red Hat 2.33.x
- Red Hat build of OpenTelemetry Operator 0.152.x or 0.158.x
- Tempo Operator 0.22.x
- OpenShift User Workload Monitoring
- OpenShift Data Foundation / NooBaa object storage
- OpenShift Service Mesh Console (OSSMC) plugin (default)
- OpenShift distributed tracing console UI (default)

The 3.4 baseline in `v3/v3.4/` is preserved unchanged. This 3.5 baseline
uses only the authoritative deployment content under `manifests/`, `templates/`,
`storage/odf/`, `optional/`, `bookinfo/`, and `scripts/`. The old vendored
`istio-1.30.3/` distribution is deliberately not copied; it is not used by
the canonical apply flow.

## Supported data paths

```text
Envoy/Istio proxy metrics
  -> /stats/prometheus
  -> PodMonitor / ServiceMonitor
  -> OpenShift User Workload Monitoring
  -> Prometheus / Thanos
  -> Kiali

Envoy/Istio traces
  -> OTLP/gRPC :4317
  -> OpenTelemetry Collector
  -> authenticated OTLP/gRPC :8090
  -> Tempo Gateway
  -> TempoStack
  -> ODF / NooBaa S3

Kiali
  -> Thanos Querier :9091 using the Kiali service-account token
  -> Tempo Gateway :8080 using the Kiali service-account token
```

Grafana is intentionally not part of the core stack. Two OpenShift console integrations are deployed by default:

- `OSSMConsole/ossmconsole`, managed by the Kiali Operator, provides the **Service Mesh** navigation and embedded Kiali views.
- `UIPlugin/distributed-tracing`, managed by the Cluster Observability Operator, provides **Observe -> Traces**.

## Security and RBAC contracts

The core deployment creates explicit roles **and role bindings**:

- `tempo-mesh-traces-writer`
  - `CREATE` on tenant resource `tempo.grafana.com/mesh`, `resourceNames: traces`
  - bound to `system:serviceaccount:istio-system:otel-collector`
- `tempo-mesh-traces-reader`
  - `GET` on tenant resource `tempo.grafana.com/mesh`, `resourceNames: traces`
  - bound to `system:serviceaccount:istio-system:kiali-service-account`
- `cluster-monitoring-view`
  - bound to `system:serviceaccount:istio-system:kiali-service-account`

The optional OpenShift distributed tracing UI can additionally bind
`system:authenticated` to `tempo-mesh-traces-reader`. That is deliberately
optional because it grants every authenticated OpenShift user tenant-level trace
read access. Replace the subject with a narrower Group/User when appropriate.

ODF credentials are generated by the ObjectBucketClaim and are never committed.

## Hands-on lab: OCP 4.22 + OSSM 3.5 + ODF/NooBaa + Tempo

This section is the **complete, repeatable lab runbook** for the AWS-based OpenShift
4.22 deployment validated during the OSSM 3.5 migration. Follow it **in order** on
a new cluster; on an existing cluster, skip directly to [revalidate the deployed
stack](#6-revalidate-an-existing-deployment). Every step distinguishes a
*Kubernetes resource existing* from the *service being usable*.

### 0. Architecture and responsibilities

```text
AWS EBS / gp3-csi       ODF Operator 4.22 -> StorageCluster/ocs-storagecluster
    |                                      |
    +-- NooBaa PostgreSQL PVCs            +-- standalone MCG / NooBaa
    +-- default BackingStore PVC (50 GiB)      |
                                               +-- OBC/tempo-odf (Bound)
                                                   +-- Secret/tempostack-odf
                                                       +-- TempoStack/mesh

Client -> OpenShift Route -> Bookinfo Istio ingress -> productpage
                                                    +-> details
                                                    +-> reviews -> ratings
                    |                                  |            |
                    +----------- Envoy tracing -------+------------+
                                    | OTLP/gRPC :4317
                              OpenTelemetry Collector
                                    | secured OTLP/gRPC :8090
                                 Tempo Gateway -> Tempo -> NooBaa

Envoy Prometheus metrics -> PodMonitor/ServiceMonitor -> UWM/Thanos -> Kiali
```

**Components and tested versions:** OCP 4.22.18; OSSM Operator 3.5.0,
Istio `v1.31-latest`; Kiali Operator 2.33.1; Red Hat OpenTelemetry 0.158.0;
Tempo Operator 0.22.0 with Tempo 2.10.8; ODF 4.22.7; NooBaa PV-backed MCG.
The scripts also recognize the documented alternate OpenTelemetry 0.152 family.
The examples are **AWS/EBS-specific** (`gp3-csi`), not general templates for
ROSA, disconnected clusters, another cloud, or external S3.

**What must already exist:** a healthy OCP 4.22 cluster, working `oc` login,
cluster-admin privileges for installing operators and cluster resources,
`redhat-operators` CatalogSource exposing ODF `stable-4.22`, the other OSSM
operator subscriptions, and AWS CSI provisioning via `gp3-csi`. Local tools:
`bash`, `oc`, `jq`, `sed`, `awk`, `curl`, `base64` and `python3` for the update
installer. No AWS root credentials should be fabricated by this runbook.

### 1. Confirm the cluster and initialize an immutable Tempo tenant

```bash
oc whoami
oc get clusterversion version
oc get nodes
oc get storageclass
oc get csv -A | grep -Ei 'servicemesh|kiali|tempo|opentelemetry|observability'

cd ~/Documents/POCs/ServiceMesh/v3/v3.5
./scripts/init-env.sh
# The script creates .env only if absent and generates the UUID only if empty.
grep '^TEMPO_TENANT_ID=' .env
./scripts/render.sh
```

Expected: all nodes `Ready`, `gp3-csi` present, and a nonempty
`TEMPO_TENANT_ID` UUID. `render.sh` writes the generated TempoStack/Kiali
configuration under `rendered/`. **Do not** execute `cp env.example .env`
when `.env` already exists: replacing it can reset the tenant ID and other
settings. Do not commit `.env`, generated S3 secrets, AWS access keys, or
service-account tokens to Git.

The main `.env` options are:

| Variable | Default | Meaning |
| --- | --- | --- |
| `BOOTSTRAP_MCG` | `0` | Opt-in to ODF/MCG creation *before* `apply.sh` validation |
| `CHECK_MCG_HEALTH` | `1` | Require real NooBaa/BackingStore/BucketClass/PVC health |
| `MCG_TIMEOUT_SECONDS` | `1200` | Bounded MCG bootstrap/reconciliation deadline |
| `APPLY_MESH_BASE` | `0` | Preserve an existing healthy Istio; use `1` for a new mesh |
| `RUN_E2E` | `1` | Require the full final data-path acceptance test |
| `E2E_REQUESTS` | `200` | Unsampled-control-free normal Bookinfo traffic |
| `E2E_FORCED_TRACES` | `12` | Client-directed exact trace-ID positive controls |
| `TEMPO_LOCAL_PORT` | `18080` | Local port for the private Tempo gateway query |
| `THANOS_LOCAL_PORT` | `19091` | Local port for secured UWM/Thanos queries |

Environment variables supplied before a command override the same values in
`.env`. `--relax-version-checks` relaxes **only** version family checks; it
must never bypass missing APIs, failed storage health, security, or E2E gates.

### 2. Install the ODF 4.22 operator (first time only)

Confirm the advertised channel:

```bash
oc get packagemanifest odf-operator -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{"\n"}{end}'
# Must list stable-4.22
```

The scripted route is preferred because it is idempotent and refuses to
silently replace incompatible existing storage resources:

```bash
./storage/odf/bootstrap-mcg.sh
```

**What the script does, step by step:** (a) verifies OCP 4.22 and the
`gp3-csi` StorageClass; (b) creates `openshift-storage` if missing; (c)
applies `storage/odf/00-operatorgroup.yaml` and
`storage/odf/01-odf-subscription.yaml`; (d) waits for `odf-operator`,
`ocs-operator` and `mcg-operator` CSVs to be `Succeeded`, plus their CRDs; (e)
creates `storage/odf/02-mcg-storagecluster.yaml` only when absent; (f) waits
for the **usable PV-backed object data path**, not just running operators.

For a classroom demonstration, the equivalent *individual installation*
commands are:

```bash
oc create namespace openshift-storage --dry-run=client -o yaml | oc apply -f -
oc apply -f storage/odf/00-operatorgroup.yaml
oc apply -f storage/odf/01-odf-subscription.yaml
oc get subscriptions -n openshift-storage
oc get csv -n openshift-storage
```

A CSV showing `Pending` immediately after installation can be normal; watch
for `Succeeded` for the ODF, OCS and MCG dependencies. If it stays Pending,
inspect `oc describe csv <name> -n openshift-storage` and namespace events.
**Operator installation does not create the gateway.** The next step is
mandatory. Never install a full Ceph storage cluster merely to satisfy this
specific lab's object-storage requirement.

### 3. Configure standalone MCG using existing AWS EBS volumes

The authoritative manifest is
`storage/odf/02-mcg-storagecluster.yaml`:

```yaml
apiVersion: ocs.openshift.io/v1
kind: StorageCluster
metadata:
  name: ocs-storagecluster
  namespace: openshift-storage
spec:
  multiCloudGateway:
    dbStorageClassName: gp3-csi
    reconcileStrategy: standalone
```

`bootstrap-mcg.sh` manages this automatically. To demonstrate the manual API
operation **only after** the operator and CRDs are installed:

```bash
oc get crd storageclusters.ocs.openshift.io
oc get crd noobaas.noobaa.io
oc get crd objectbucketclaims.objectbucket.io
oc apply --dry-run=server -f storage/odf/02-mcg-storagecluster.yaml
oc apply -f storage/odf/02-mcg-storagecluster.yaml
```

**Do not confuse APIs:** with ODF 4.22, the verified CLI deployment uses
`StorageCluster` (`storageclusters.ocs.openshift.io`). An unavailable
`storagesystem` resource does not mean the ODF operator failed. Check the
actual APIs with `oc api-resources | grep -Ei 'storagecluster|noobaa|objectbucket'`.

During the initial reconciliation, these states were observed and **are not
failures by themselves**:

| Resource | Initial | Acceptable final state |
| --- | --- | --- |
| `StorageCluster/ocs-storagecluster` | `Progressing` | `Ready`, or `Progressing` with the verified healthy PV-pool path |
| `NooBaa/noobaa` | `Connecting` then `Configuring` | `Ready` |
| `noobaa-core-0` | `ContainerCreating` | All containers Ready |
| `noobaa-endpoint-*` | Created later | Ready |
| `noobaa-default-backing-store` | Absent then `Creating` | `Ready`, condition `OPTIMAL` |
| `noobaa-default-bucket-class` | Absent | `Ready` |
| `openshift-storage.noobaa.io` | Absent | StorageClass exists |
| NooBaa data PVC | Pending/absent | `Bound`, backed by `gp3-csi` |

A `Running` database pod, a `Succeeded` operator CSV, or an existing OBC CRD
is *not* sufficient. The gateway's actual backing store has to be usable.

### 4. Verify MCG health and understand the AWS credential warning

The supported one-command acceptance check is:

```bash
./storage/odf/check-mcg.sh --quick
```

For a didactic inspection of the whole data path:

```bash
oc -n openshift-storage get storageclusters.ocs.openshift.io
oc -n openshift-storage get noobaas.noobaa.io
oc -n openshift-storage get backingstores.noobaa.io
oc -n openshift-storage get bucketclasses.noobaa.io
oc -n openshift-storage get pods,pvc
oc get storageclass openshift-storage.noobaa.io

oc -n openshift-storage get backingstore noobaa-default-backing-store -o json |
  jq '{phase:.status.phase, type:.spec.type, pvPool:.spec.pvPool,
       conditions:.status.conditions}'
```

For the validated AWS lab, the BackingStore was `pv-pool` with a **50 GiB
`gp3-csi` data PVC**; separate PostgreSQL database PVCs do not prove the
BackingStore is healthy. The BucketClass must reference this BackingStore and
be `Ready`.

**Credential warning encountered in the lab:** the Cloud Credential Operator
was healthy while `CredentialsRequest/openshift-storage/noobaa-aws-cloud-creds`
reported `CredentialsProvisionFailure`, because the root Secret
`kube-system/aws-creds` was absent. The generated
`openshift-storage/noobaa-aws-cloud-creds-secret` was also absent. Nevertheless,
NooBaa and the local `pv-pool` BackingStore became `Ready`, the BucketClass
became `Ready`, and the OBC successfully bound. This is an *observed outcome
for this PV-backed lab*, not proof that AWS credentials are unnecessary for
other ODF configurations. The health checker **warns** on this separate
CredentialsRequest but still demands a healthy local PV-backed data path.

To diagnose (without exposing keys):

```bash
oc get co cloud-credential
oc get cloudcredential.operator.openshift.io cluster -o yaml
oc -n openshift-storage get credentialsrequest noobaa-aws-cloud-creds -o json |
  jq '{secretRef:.spec.secretRef, conditions:.status.conditions}'
oc -n kube-system get secret aws-creds -o name
oc -n openshift-storage get secret noobaa-aws-cloud-creds-secret -o name
```

An empty `.spec.credentialsMode` does **not** uniquely determine whether the
cluster uses Mint, Passthrough, or an external credential strategy. Investigate
AWS STS/IAM trust and the CCO mode only when this is relevant to an actual
required data path. **Never** fabricate an `aws-creds` Secret, switch CCO modes,
or delete a StorageCluster/PVC just to hide a warning. Production designs
should explicitly address ODF database backups, AWS IAM, backup/restore,
capacity, availability, and Red Hat support requirements. This one-PVC lab
is not a high-availability production object store.

### 5. Deploy Tempo, Istio, OpenTelemetry, Kiali, and Bookinfo

With MCG healthy and the Tempo tenant initialized:


supported option is `BOOTSTRAP_MCG=1 APPLY_MESH_BASE=1 ./scripts/apply.sh`,

The core `apply.sh` steps are retained: namespace bootstrap and full
server-side validation; UWM; IstioCNI/Istio; Telemetry and monitors; Tempo
OBC and Secret; Tempo tenant RBAC; TempoStack; OTel SA/RBAC/Collector; Kiali
and console integrations; Bookinfo with ingress/Route; readiness; and the
final E2E. Re-running a healthy installation should not require deleting any
resources. **The update does not rewrite the working Istio, mesh Telemetry,
Collector, Tempo, or Bookinfo manifests.**

```bash
oc -n tempo get objectbucketclaim tempo-odf        # phase=Bound
oc -n tempo get tempostack mesh                    # READY=True
```

these credentials into the README, logs, or Git repository.

### 7. Why the original 12 forced W3C traces failed

The first E2E run succeeded for Bookinfo HTTP traffic and found **unrelated,
complete distributed traces** in Tempo, but the exact client-generated W3C
trace IDs returned HTTP `404`. The known Tempo trace could be queried by ID
and contained `istio-ingressgateway.bookinfo`, `productpage.bookinfo`,
`details.bookinfo`, `reviews.bookinfo` and `ratings.bookinfo`: therefore the
**OTLP → Collector → Tempo storage/query path already worked**. The issue was
specific to deterministic client-directed tracing, not an ODF or Tempo outage.

The live ingress Envoy `config_dump` revealed:

```yaml
provider: envoy.tracers.opentelemetry
random_sampling: 10
client_sampling: 100
overall_sampling: 100
spawn_upstream_span: true
```

The ingress Deployment uses label **`istio=ingressgateway`**, not
`app=istio-ingressgateway`. The incorrect selector returns an empty PodList.
Use the included observer:

```bash
./scripts/check-envoy-tracing.sh
```

Or reproduce manually using actual Envoy configuration keys in
`snake_case` (not the camelCase names of protobuf documentation):

```bash
GW="$(oc -n bookinfo get pod -l istio=ingressgateway \
  -o jsonpath='{.items[0].metadata.name}')"
oc -n bookinfo exec "$GW" -c istio-proxy -- \
  pilot-agent request GET config_dump > /tmp/ossm35-ingress-envoy.json
jq '[.. | objects | select(.tracing?.provider?.name == "envoy.tracers.opentelemetry") |
  {provider:.tracing.provider.name,
   grpc:.tracing.provider.typed_config.grpc_service.envoy_grpc.cluster_name,
   random:.tracing.random_sampling.value,
   client:.tracing.client_sampling.value}] | unique' /tmp/ossm35-ingress-envoy.json
```

**Verified experimental correction:** an external `curl` using both
`traceparent: 00-TRACE_ID-SPAN_ID-01` and
`x-client-trace-id: TRACE_ID` produced a Tempo `HTTP 200` lookup for the
**exact** injected ID. The first successful lookup was initially partial
(`productpage`, `details`), and the next lookup contained ingress, productpage,
details and reviews. Tempo does not guarantee all spans have arrived on the
first `200`; the E2E must continue polling until the full service chain exists.

The updated E2E change therefore adds `x-client-trace-id` **only to positive
controls**. Normal requests retain 10% random sampling. The W3C
`trace-flags=00` negative control has **no** force-tracing header. The test
still requires every injected trace to contain ingress, productpage, details
and reviews, plus at least one forced trace covering ratings. We are not
switching tracer providers, raising random sampling to 100%, or weakening the
exact trace-ID assertion.

### 8. Tempo and Thanos port-forward collisions

The E2E uses local forward ports `18080` (Tempo gateway) and `19091`
(Thanos). The old sequence could generate all 200 normal and 12 forced test
requests **before** discovering a stale manual Tempo port-forward on 18080.
The new script opens both forwards before sending traffic, and fails early
with a specific message on `bind: address already in use`.

```bash
# Find any old/manual forwarding processes without killing unrelated ones:
ss -ltnp '( sport = :18080 )'
pgrep -af 'oc.*port-forward.*tempo-mesh-gateway'

# Easiest non-disruptive approach:
TEMPO_LOCAL_PORT=18081 ./scripts/e2e-check.sh --fast
# If Thanos is also occupied:
TEMPO_LOCAL_PORT=18081 THANOS_LOCAL_PORT=19092 ./scripts/e2e-check.sh --fast
```

The script's exit trap terminates **only its own** background forwards. If
that port is occupied, change the environment variable rather than deleting
the running Tempo Service, rerunning `apply.sh`, or changing cluster networking.

### 9. Troubleshooting matrix

| Symptom | Root-cause-oriented check | Action |
| --- | --- | --- |
| ODF CSV `Pending` immediately after Subscription | `oc get csv -n openshift-storage` and events | Check dependency installation/reconciliation; do not assume failed from initial Pending |
| `oc get storagesystem` unknown type | `oc api-resources \| grep -Ei 'storagecluster\|noobaa'` | Use `StorageCluster` on this ODF 4.22 configuration |
| No `NooBaa/noobaa` or OBC StorageClass | `oc get storageclusters.ocs.openshift.io -n openshift-storage` | Install standalone MCG CR after operators succeed |
| `NooBaa=Connecting/Configuring` | `oc get pods,pvc -n openshift-storage` | Check core/endpoint, PostgreSQL and backing-store provisioning |
| `NooBaa=Ready` but BackingStore `Creating` | `oc describe backingstore ...` | Wait for the actual data PVC and backing-store `OPTIMAL` |
| AWS CredentialsRequest says `aws-creds` absent | Inspect CCO and required BackingStore type | Do not invent credentials; assess separately from healthy local PV-pool |
| Tempo OBC not `Bound` | `oc get obc -n tempo` and `check-mcg.sh --quick` | Fix NooBaa bucket allocation before Tempo |
| Known Tempo trace has 5 services, forced trace 404 | Check effective tracer + `x-client-trace-id` | Add client-directed header only to positive controls |
| Exact trace HTTP 200 but missing ingress/reviews | Poll again; inspect service names | Allow spans to arrive; retain full-chain gate |
| `curl_bookinfo: command not found` | Function exists inside `scripts/e2e-check.sh` | Edit/rerun script, do not invoke Bash helper from interactive shell |
| `app=istio-ingressgateway` selector matches zero pods | `oc get pods -n bookinfo -l istio=ingressgateway` | Use gateway's actual `istio` label |
| Tempo port-forward cannot bind 18080 | `ss -ltnp '( sport = :18080 )'` | Run with `TEMPO_LOCAL_PORT=18081` or stop only the identified old forward |
| E2E metrics fail after traces succeed | Thanos baseline/after query and UWM PodMonitors | Diagnose monitoring path separately; do not weaken metrics assertion |

### 10. Completion and acceptance checklist

- [ ] All required operator CSVs `Succeeded` and OSSM 2 coexistence gate reviewed.
- [ ] `NooBaa/noobaa` `Ready`; default PV-backed BackingStore and BucketClass `Ready`.
- [ ] BackingStore's own `gp3-csi` PVC `Bound`; OBC StorageClass exists.
- [ ] `tempo/tempo-odf` `Bound`; TempoStack `Ready`, gateway endpoints usable.
- [ ] IstioCNI/Istio healthy at the target 1.31 family.
- [ ] OpenTelemetry Collector and Kiali ready; RBAC authorizations verified.
- [ ] Bookinfo ingress and all service dependencies return HTTP 200.
- [ ] 200 normal requests with zero HTTP failures; random 10% traces found.
- [ ] All 12 forced exact IDs found with complete ingress/productpage/details/reviews spans; at least one includes ratings.
- [ ] Negative `trace-flags=00` control not stored; Collector shows no export errors.
- [ ] Thanos `istio_requests_total` increases during generated traffic.
- [ ] `./scripts/e2e-check.sh` finishes with `E2E PASS`.

**Result reported so far:** the gateway, BackingStore and Tempo deployment
were observed healthy, and one exact client-directed W3C trace was retrieved
with the required four-service chain. A complete 12-trace E2E PASS after the
patch has **not** yet been observed; run it to close the acceptance checklist.

## Configure

```bash
cd v3/v3.5

cp env.example .env
uuidgen
vi .env
```

Set the generated UUID as `TEMPO_TENANT_ID` and keep it stable for the lifetime
of `TempoStack/mesh`.

The default mesh namespaces are:

```bash
MESH_NAMESPACES="istio-system bookinfo"
```

Add every namespace whose Istio sidecars must be scraped.

### Existing Istio control plane

The default is:

```bash
APPLY_MESH_BASE=0
```

In this mode the scripts refuse to continue unless the existing `Istio` and
`IstioCNI` resources are Ready, use the Istio 1.31 family, and the live Istio resource
already defines the required `otel-tracing` provider at:

```text
otel-collector.istio-system.svc.cluster.local:4317
```

If you intentionally want this bundle to reconcile those resources:

```bash
APPLY_MESH_BASE=1
```

Fresh reconciliation targets `v1.31-latest` via the Sail Operator. Upgrading an
existing Istio 1.30 control plane is **not** automatic in preserve mode. Use
`APPLY_MESH_BASE=1` only when an Istio 1.31 upgrade is intentional and
the operator supports that version. To test preserving an older control plane,
use `--relax-version-checks` while keeping Ready, telemetry and E2E gates.

## Validate before applying

Load `.env` automatically by keeping it in this directory, then run:

```bash
./scripts/check-prereqs.sh
./scripts/render.sh
./scripts/validate.sh
```

`validate.sh` performs shell syntax checks, authorization checks, selectorless
Telemetry conflict detection, and **server-side dry-run** validation against the
CRDs actually installed on the cluster. On a brand-new cluster, Kubernetes cannot
server-dry-run namespaced objects until their target Namespaces exist. For only
that bootstrap condition, `validate.sh` performs strict client dry-run validation
and marks the server checks as deferred. `apply.sh` then creates the four target
Namespaces and reruns `validate.sh`, requiring the complete server-side dry-run to
pass before it applies user-workload monitoring, Istio, Tempo, OTel, Kiali, or UI
resources.

Strict operator checks target Service Mesh 3.5.x, Kiali 2.33.x,
OpenTelemetry 0.152.x/0.158.x, Tempo 0.22.x and Cluster Observability 1.x.
The installed cluster currently demonstrates Service Mesh 3.5.0, Kiali 2.33.1,
Tempo 0.22.0-5 and Cluster Observability 1.5.4; OpenTelemetry and NooBaa
must be installed or recovered separately. Other operator versions remain
unverified unless the full CRD, server dry-run, readiness and E2E path passes.

## Opt-in version relaxation (test only)

```bash
./scripts/check-prereqs.sh --relax-version-checks
./scripts/validate.sh --relax-version-checks
APPLY_MESH_BASE=1 ./scripts/apply.sh --relax-version-checks
```

This parameter relaxes **operator CSV versions** and the **Istio minor-version
guard when preserving a control plane**. It never bypasses absent or failed
operators, missing CRDs, missing NooBaa storage, OSSM2 coexistence, RBAC,
resource readiness or E2E assertions. The flag is passed to nested scripts.
Do not use it as a claim of compatibility. The installation will remain blocked
until OpenTelemetry and the configured S3 ObjectBucketClaim dependencies exist.

## Apply

```bash
./scripts/apply.sh
```

The script executes the numbered deployment contract. Operator-managed CRs are gated on their authoritative status conditions, their generated workloads/services are checked separately, and timeouts dump CR/pod/event diagnostics. The setup is idempotent and can be rerun after a partial failure.

## Final E2E acceptance gate

`RUN_E2E=1` is the default and `apply.sh` runs `scripts/e2e-check.sh` only after the complete readiness postcheck. When Bookinfo is enabled the route URL is discovered automatically.

For iterative E2E debugging on a deployment that has already passed the normal
readiness validation, use:

```bash
./scripts/e2e-check.sh --fast
```

`--fast` jumps directly to the E2E data-path checks by skipping the exhaustive
`postcheck.sh` snapshot both before and after the E2E sequence. It still performs
the direct E2E assertions and the Tempo writer/reader authorization checks needed
by those tests. Normal `apply.sh` and a plain `e2e-check.sh` keep the full
acceptance behavior.

The test must prove **this run**, not merely observe stale telemetry. It verifies:

1. the external Bookinfo `/productpage` response and page content;
2. an independent in-mesh `ratings -> productpage` service request;
3. `E2E_REQUESTS` normal ingress requests with the configured 10% sampler and no more than `E2E_MAX_HTTP_FAILURES` failures;
4. multiple forced-sampled requests carrying unique known W3C `traceparent` trace IDs;
5. exact Tempo retrieval of every forced trace ID;
6. service-chain membership for ingress, productpage, details, reviews, plus at least one trace including ratings;
7. a W3C `traceparent` negative control with trace-flags `00` that must not be stored;
8. a separate bounded random-sampling search window requiring at least `E2E_MIN_RANDOM_TRACES` traces;
9. no OTel export/auth/TLS/drop errors since the E2E start time;
10. a **before/after** Thanos query proving `istio_requests_total{destination_service_namespace="bookinfo"}` increased by at least `E2E_MIN_METRIC_DELTA` during the test;
11. a final full readiness postcheck.

The exact-trace and before/after-metric gates prevent unrelated historical traces or counters from satisfying the test.

## OpenShift Service Mesh console

The Service Mesh menu is **not** created by the `Kiali` CR alone. The supported setup creates:

```yaml
apiVersion: kiali.io/v1alpha1
kind: OSSMConsole
metadata:
  name: ossmconsole
  namespace: openshift-operators
spec:
  version: default
  kiali:
    serviceName: kiali
    serviceNamespace: istio-system
    servicePort: 20001
```

`ENABLE_MESH_CONSOLE=1` is the default. Readiness requires `OSSMConsole/ossmconsole` to report `Successful=True`, the generated `ConsolePlugin/ossmconsole` to exist, and its backend Service to have ready endpoints. Refresh the OpenShift console after first installation.

## OpenShift tracing UI

The Cluster Observability Operator distributed tracing UI plugin is enabled by default and is distinct from OSSMC:

```bash
ENABLE_TRACING_UI=1
```

Kiali renders its `View in Tracing` links with `tempo_config.url_format: openshift` and the discovered OpenShift console Route. Set `ENABLE_TRACING_UI=0` only to opt out.

To also use the example broad reader binding:

```bash
ENABLE_TRACING_UI_RBAC=1
```

For production, prefer leaving `ENABLE_TRACING_UI_RBAC=0` and editing
`optional/15-tempo-console-reader-rbac.yaml` to target the intended user group.

## UWM safety

`manifests/01-user-workload-monitoring.yaml` is the declarative baseline for a
cluster without `cluster-monitoring-config`.

If that ConfigMap already exists, `scripts/enable-uwm.sh` **does not overwrite
it**. It requires `enableUserWorkload: true` to already be present so unrelated
cluster monitoring configuration cannot be destroyed.

## Operator-managed observability

`TempoStack/mesh` enables operator-created `ServiceMonitor` and `PrometheusRule` objects for Tempo components. `OpenTelemetryCollector/otel` enables operator-created Collector monitoring. The Collector is bounded to a 512 MiB pod limit with a 400 MiB memory-limiter hard limit and uses the non-deprecated `otlp_grpc` exporter identifier.

Tempo tenant permissions are verified with Kubernetes `SubjectAccessReview`. `oc auth can-i` is intentionally not used for `tempo.grafana.com/mesh` because this is a synthetic authorization resource consumed by the Tempo gateway and is not present in Kubernetes API discovery.

## Bookinfo setup

Bookinfo is part of the supported setup path by default (`DEPLOY_BOOKINFO=1`).
The repository vendors the Red Hat-documented sidecar-mode Bookinfo sample and
its gateway resources so installation does not depend on mutable remote YAML at
runtime:

- `bookinfo/00-bookinfo.yaml` — Red Hat OSSM 3.4 Bookinfo sample, upstream blob `28ac4f6828e21717e0198bda2a9ac7f4694458af`.
- `bookinfo/01-ingress-gateway.yaml` — Sail gateway-injection sample, upstream blob `009cfc72950fdede8c4c7fec2e0d54c098d66181` at vendoring time.
- `bookinfo/02-bookinfo-gateway.yaml` — Istio `Gateway` + `VirtualService`, upstream blob `54e86888c651268356911772fdca379f7aa8d23e`.
- `bookinfo/03-route.yaml` — declarative OpenShift `Route` equivalent to `oc expose service istio-ingressgateway`.

The `bookinfo` Namespace is labeled `istio-discovery=enabled` and
`istio-injection=enabled`. The dedicated Bookinfo ingress pod carries
`app.kubernetes.io/component=bookinfo-ingressgateway`, and the Istio
`Gateway` requires that label in addition to `istio=ingressgateway`. This
prevents another wildcard `*:8080` Gateway in a different namespace from
selecting the Bookinfo ingress workload.

`apply.sh` waits for all Bookinfo deployments,
sidecars, service endpoints, the injected ingress gateway, the Istio Gateway and
VirtualService objects, and Route admission before final validation.

See [VALIDATION.md](VALIDATION.md) for the complete readiness and final E2E
acceptance contract.

## Release-tolerant apply/readiness behavior

The deployment helpers use API-qualified resource identities and release-tolerant readiness checks. In particular, Bookinfo accepts Istio as either a classic or Kubernetes native sidecar, Service backends are read from EndpointSlice with Endpoints fallback, and Istio Gateway resources are always queried through `networking.istio.io` to avoid collisions with Kubernetes Gateway API. Generic waits parse `TYPE/NAME` and call `oc get TYPE NAME`, and individual API requests are bounded by `KUBE_API_REQUEST_TIMEOUT` (default `15s`).
